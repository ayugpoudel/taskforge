# Explaining TaskForge

**30 seconds.** A client uploads a CSV, submits a job and gets an ID immediately. Workers stream the file and generate a JSON report. PostgreSQL remembers accepted work across restarts. The interesting failure is a worker that appears dead and then resumes. Each attempt writes its own report, and only the current lease holder can publish the result.

**Two minutes.** Trace the [request sequence](ARCHITECTURE.md#implemented-request-lifecycle). Start with the HTTP boundary. A user can retry after losing the response. The request key lets PostgreSQL recognize the same submission. Move to the dispatcher boundary. A job and its publication intent commit together. A dispatcher that crashes immediately after publishing can publish twice. Move to the worker boundary. Both deliveries reference one job. The database grants a short lease and a generation. Computation happens outside the transaction. The worker writes a private candidate report, then conditionally commits its key. A client polls the authorized job and downloads that selected object. A crash between completion and acknowledgement leaves a redundant notification that another worker can safely clear.

**Five minutes.** Give the two-minute walkthrough, then take one minute each on three concrete questions. What if the old worker wakes up after a replacement finishes? Sketch two generations and two object keys. What if demand doubles? Explain admission limits, queue age and per-worker CPU measurements. What did the experiment actually establish? Draw the 1/2/4-worker benchmark table, identify the unchanged dataset and the single regex change, then describe the shared host and short batches. Use the following questions to practice the details.

| Interview question | Example answer and design tradeoff | Implementation to inspect |
|---|---|---|
| Why return an ID? | A report may outlive the connection. Synchronous HTTP ties up a request thread and retrying can repeat work. A durable job lets clients poll later. | Api.upload, JobStore.create |
| Why separate workers? | Separate processes let us add CPU capacity and restart a worker while the API still accepts jobs. An in-process executor shares the API's failure and resource limits. | StreamWorker, compose.yml |
| What does the database remember? | Dataset ownership, jobs, attempts, transitions, and outbox events survive process death. The creation transaction records both the job and the intent to send it. Two independent writes would leave a crash window. | Flyway migrations, JobStore.create |
| Why use Redis as well? | A consumer group distributes small job references and tracks unacknowledged messages. A PostgreSQL-only queue with SKIP LOCKED would be simpler for a small system. Redis lets us exercise pending delivery and scale consumers separately. | RedisQueue.publish, recoverPending, acknowledge |
| What happens after duplicate submission or delivery? | At submission, an owner-scoped key matches the payload or produces a conflict. At execution, a conditional claim and a guarded final update protect the result. A request key alone cannot protect a worker from redelivery. | JobStore.create, claim, complete |
| Why use heartbeats and a generation? | A lease detects an absent worker. A heartbeat extends it during legitimate work. A generation distinguishes the new owner from a paused old one. Holding a SQL lock throughout parsing would occupy a connection for the whole job. | JobStore.heartbeat, recoverExpired, complete |
| What if a worker already uploaded bytes? | Each attempt writes to a separate private key. Only the winning key is referenced by the job. Sharing one mutable key would allow a delayed write to corrupt a successful result. Cleanup of other keys is eventual. | JobRunner.run, StorageCleanup, Api.result |
| Which failures merit a retry? | A temporary dependency failure may clear. Persist the next eligible time, apply backoff and jitter, and cap attempts. Malformed CSV stays malformed. Keeping the timer only in memory would lose retry scheduling on restart. | JobStore, Dispatcher, CsvJobProcessor |
| How does streaming bound memory? | Keep one record plus per-column accumulators. Cap field length, column count and total upload bytes. A whole-file list would grow with row count. Invalid-width rows are counted separately from valid aggregates. | CsvAnalytics.analyze, CsvSyntaxReader, LimitedInputStream |
| What if cancellation races with completion? | The database serializes the two state changes. A cancelled job cannot publish a result. The physical worker stops cooperatively at checkpoints. A deadline also limits time spent waiting and retrying. | JobStore.cancel, complete, JobRunner.run |
| What prevents overload? | Limit active jobs at admission and simultaneous leases per owner. Each worker has bounded execution slots. Accepting all traffic would convert overload into growing wait time and storage use. | JobStore.create, claim, StreamWorker |
| How do you diagnose a slowdown? | Compare queue age, outbox backlog, worker activity and stage timers. A growing outbox points upstream of computation. During benchmarking calculation dominated reads. Reusing one regex increased one-worker median throughput 3.69 times. | TaskMetrics, CsvAnalytics, docs/BENCHMARKS.md |
| How can someone reproduce it? | Compose runs independent roles with actual PostgreSQL, Redis and MinIO. CI uses real-service fixtures plus a clean Gradle check. Mocking those services alone would miss SQL and delivery races. AWS is a configuration-only design. | Dockerfile, .github/workflows/ci.yml, PlatformIntegrationTest |

For failure examples distinguish observations from guarantees. The worker-kill load case recorded 13 attempts for 12 completed jobs. The recorded three-second Redis outage delayed a batch almost 54 seconds. Neither measurement sets a recovery deadline. Read the [raw measurements](BENCHMARKS.md), [implementation review](RELIABILITY_REVIEW.md) and [architecture decisions](adr/) before discussing other workloads or deployment environments.
