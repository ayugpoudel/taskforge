# ADR-0005: Persist delayed retries and keep dead-letter state in PostgreSQL

Date: 2026-11-19. Status: accepted.

Problem: transient faults need retry, invalid input does not; in-memory timers vanish on process restart and immediate requeue can overwhelm a failing dependency.

Requirements: bounded attempts, durable next-run time, jitter, diagnostics without source data. Alternatives: immediate broker redelivery, sleep in worker threads, broker-specific delayed queues, SQL next-attempt scheduling.

Decision: RETRY_WAIT plus PostgreSQL next_attempt_at and a due outbox event. Equal-jitter exponential delay starts at a 500–1000 ms window and caps at 30–60 s; the default attempt budget is three. Invalid CSV is permanent. Exhaustion becomes FAILED with attempt history and sanitized codes; this database terminal state is the dead-letter record. No separate DLQ stream is necessary to preserve the diagnostics.

Administrative replay is explicit, restricted to a configured admin identity, and limited to failed non-invalid-input jobs. It resets the per-run budget and deadline while keeping generation monotonic and all earlier attempt records. No admin token is generated by default. Replaying unchanged invalid CSV is rejected.

Tradeoffs: due polling adds bounded SQL work; not strict FIFO; a new attempt may repeat computation. Attempts are not hidden by resetting history. Administrative replay does not fix a malformed source and is not automatic.

Rejected: thread sleeps consume worker slots and cannot durably schedule; immediate retries create hot loops; a separate broker DLQ would duplicate authoritative SQL failure state at this scale.

Evidence: RetryPolicy, JobStore.finishFailure/recoverExpired/replay, V3 outbox indexes; bounded-jitter/exhaustion/permanent-failure tests. See TESTING.md for executed status.

Revisit: retry volume or timing precision justifies a dedicated scheduler, or new workloads need more detailed error classification.
